## Когда использовать

- Когда уже есть дизайн сервиса и его надо критически проверить
- Когда нужен peer review до реализации или перед архитектурным комитетом
- Когда хочется получить не только критику, но и приоритизированные remediation steps

**Когда брать `quick`:** нужен быстрый review за один проход — например, чтобы быстро понять, есть ли красные флаги, или показать команде «вот что я бы спросил».

**Когда брать `critique`:** review идёт в комитет / на запись / перед решением о реализации. Модель сначала выдаёт draft, потом сама ловит свои слабые места (где была слишком резкой, слишком мягкой, что пропустила), и потом переписывает improved версию. Стоит вдвое дороже по токенам, но качество заметно выше.

## Что подставить

- `{{mode}}` — enum: `quick | critique`
- `{{architecture_description}}` — string or link, e.g. `текст design doc или ссылка на Confluence`
- `{{business_context}}` — string, e.g. `обрабатываем платежи b2c, peak в чёрную пятницу x10`
- `{{tech_stack}}` — string, e.g. `Go 1.22, Postgres 16, Redis, Kafka`
- `{{scale_requirements}}` — string, e.g. `500 RPS baseline, 5k RPS peak; p99 < 500ms`
- `{{team_context}}` — string, e.g. `5 backend mid, 1 senior, нет SRE`
- `{{specific_concerns}}` — list, e.g. `согласованность данных при refund; idempotency на retry`
- `{{compliance_needs}}` — string, e.g. `PCI DSS SAQ-D; GDPR; данные не покидают EU`

## Definition of done

Универсальный минимум — см. [Definition of done](./standards.md#2-definition-of-done).

Специфичные критерии:

- Каждый finding имеет severity (`critical | high | medium`) и предлагаемого owner-а (`team | role`)
- Где проблема зависит от масштаба — указан порог («проявится при RPS > X»)
- Вердикт явно один из `approve | approve with major changes | request redesign`
- Топ-3 риска — это не пересказ findings, а отдельная приоритизация

В `critique` режиме дополнительно:

- Self-review содержит как минимум 4 явных вопроса к своему draft-у (что пропустил, где был резок, где был мягок, защитимы ли severity)
- Refined версия отличается от draft — есть хотя бы 2 содержательных изменения (новый finding, переоценка severity, переформулировка action item)
- В конце refined версии есть короткий `Изменения относительно draft` — что изменилось и почему

## Промт

```text
Выступай как Principal Software Architect, который проводит formal architecture review для критичного сервиса.

Режим выполнения: {{mode}}

Контекст:
- Описание архитектуры: {{architecture_description}}
- Бизнес-контекст: {{business_context}}
- Технологический стек: {{tech_stack}}
- Требования к масштабу: {{scale_requirements}}
- Контекст команды: {{team_context}}
- Специальные зоны риска / concern areas: {{specific_concerns}}
- Compliance / regulatory needs: {{compliance_needs}}

Если для качественного ответа не хватает контекста — задай до 7 коротких уточняющих вопросов одним сообщением. Если критичных пробелов нет — действуй с разумными дефолтами и в начале ответа приведи раздел `Допущения` со списком того, что ты предположил.

Проведи review по следующим направлениям:
1. Domain boundaries и cohesion
2. Data ownership и consistency model
3. API / event contracts
4. Scalability bottlenecks
5. Reliability / fault tolerance
6. Security / privacy
7. Operability / observability
8. Team fit и operational complexity

────────────────────────────────────────────────────────────────
### Если {{mode}} = quick

Выдай review в один проход. Структура ответа ниже (раздел «Структура review»).

────────────────────────────────────────────────────────────────
### Если {{mode}} = critique

Выдай ответ в три явно помеченные фазы. Не пропускай ни одну, не меняй порядок.

## Фаза 1 — Draft

Выдай полный review по структуре ниже (раздел «Структура review»). Не редактируй его в процессе — это именно черновик.

## Фаза 2 — Self-review

Критически проверь свой draft. Ответь на эти 4 вопроса по очереди и подробно (не одним предложением):

1. **Что я пропустил?** Перечисли 3-5 вероятных слепых зон — направлений, по которым я прошёлся поверхностно или не прошёлся вообще. Указывай конкретно: «не проверил, как ведёт себя система при медленных потребителях Kafka», а не «scalability мог копнуть глубже».
2. **Где я был слишком резок?** Какие severity я завысил, какие findings раздуты, где я переписываю архитектуру вместо того, чтобы критиковать конкретный изъян. Приведи 1-3 примера.
3. **Где я был слишком мягок?** Что я аккуратно обошёл, где severity занижен, где я написал «вероятно стоит рассмотреть» вместо чёткой позиции. 1-3 примера.
4. **Защитимы ли severity?** Возьми 3 findings из draft. Для каждого спроси себя: если автор дизайна возражает «это не critical, потому что X» — у меня есть ответ? Если нет — пересмотри severity.

После 4 вопросов кратко (3-5 пунктов) сформулируй: «что я меняю в refined версии».

## Фаза 3 — Refined review

Перепиши review целиком по той же структуре, что и draft, с учётом self-review. Минимум 2 содержательных отличия от draft (новый finding, переоценка severity, переформулировка action item, изменение вердикта).

В конце добавь блок `Изменения относительно draft`:
- finding X добавлен — основание: …
- severity Y повышен с medium до high — основание: …
- action item Z переформулирован — основание: …

────────────────────────────────────────────────────────────────

## Структура review

1. [обязательно] Executive summary
2. [обязательно] Общая оценка зрелости архитектуры по шкале 1-10
3. [обязательно] Топ-3 критических риска (отдельная приоритизация, не дубль findings)
4. [обязательно] Список findings по severity:
   - critical
   - high
   - medium
5. [обязательно] Для каждого finding:
   - в чём проблема
   - почему это опасно
   - какой realistic fix
   - предполагаемый owner (team / role)
   - порог, при котором это проявится (если зависит от масштаба)
6. [обязательно] Вердикт:
   - approve
   - approve with major changes
   - request redesign

Не делай так:
- Finding без severity и без owner.
- «Переписать всё» как рекомендация без обоснования.
- Пересказывать описание архитектуры вместо критики.
- Топ-3 риска, который дублирует findings — это должна быть отдельная приоритизация.
- В critique режиме: self-review одним предложением «всё ок, ничего не меняю» — это не self-review, это отказ от работы.
- В critique режиме: refined версия, идентичная draft — значит, self-review был фиктивным.
- В critique режиме: пропустить фазу 2 и сразу выдать refined.

Требования:
- Будь критичен, но прагматичен
- Не советуй "переписать всё" без необходимости
- Если проблема зависит от масштаба, укажи при каком пороге она проявится
- Чётко отделяй факты от предположений

Формат ответа:
- Для quick: findings → open questions / assumptions → короткое summary
- Для critique: Фаза 1 (draft) → Фаза 2 (self-review) → Фаза 3 (refined) → Изменения относительно draft
```
