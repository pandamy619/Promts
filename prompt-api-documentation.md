## Когда использовать

- Когда нужно быстро оформить документацию по endpoint-спеке
- Когда важно, чтобы все endpoints описывались в едином формате
- Когда хочется снизить галлюцинации при генерации API-доков

## Что подставить

- `{{service_name}}` — string, e.g. `payments-api`
- `{{method}}` — enum: `GET | POST | PUT | PATCH | DELETE`
- `{{path}}` — string, e.g. `/v1/payments/{id}`
- `{{endpoint_purpose}}` — string, e.g. `вернуть детали платежа по id`
- `{{parameters}}` — list, e.g. `id (path, uuid, required); include (query, csv, optional)`
- `{{request_schema}}` — string, e.g. `JSON-schema или ссылка на модель`
- `{{response_schema}}` — string, e.g. `JSON-schema или ссылка на модель`
- `{{error_codes}}` — list, e.g. `404 PAYMENT_NOT_FOUND; 403 FORBIDDEN; 409 STATE_CONFLICT`
- `{{auth_type}}` — enum: `jwt | oauth2 | api_key | none`
- `{{rate_limits}}` — string, e.g. `100 req/min per token`

## Definition of done

Универсальный минимум — см. [Definition of done](./standards.md#2-definition-of-done).

Специфичные критерии:

- В выходе нет полей, которых нет во входной спецификации (или они помечены `TBD`)
- В таблице параметров для каждого поля заполнены: имя, где передаётся, тип, обязательность, описание
- Раздел `Ошибки` содержит все коды из `{{error_codes}}`, без пропусков
- Приведены и пример запроса, и пример успешного ответа — реальные значения, не плейсхолдеры

## Промт

```text
Сгенерируй аккуратную и строгую API-документацию для endpoint сервиса.

Контекст:
- Сервис: {{service_name}}
- Endpoint: {{method}} {{path}}
- Назначение: {{endpoint_purpose}}
- Parameters / query / path / headers: {{parameters}}
- Request schema: {{request_schema}}
- Response schema: {{response_schema}}
- Error codes: {{error_codes}}
- Authentication: {{auth_type}}
- Rate limits / особые ограничения: {{rate_limits}}

Если для качественного ответа не хватает контекста — задай до 3 коротких уточняющих вопросов одним сообщением. Если критичных пробелов нет — действуй с разумными дефолтами и в начале ответа приведи раздел `Допущения` со списком того, что ты предположил.

Задача:
1. [обязательно] Написать короткое и понятное описание endpoint.
2. [обязательно] Перечислить все параметры с типом, required/optional и назначением.
3. [обязательно] Сгенерировать реалистичный пример запроса.
4. [обязательно] Сгенерировать пример успешного ответа.
5. [обязательно] Описать ошибки и причины их возникновения.
6. [обязательно] Указать требования по авторизации, ограничения и важные замечания.

Не делай так:
- Примеры с outdated полями, которых нет в схеме.
- Дефолтные значения «по умолчанию» без указания, что это значит и откуда взялось.
- Ошибка `500` без описания, при каких условиях она реально возникает.
- Текст вида «smart, fast, scalable» — пустые маркетинговые прилагательные.

Guardrails:
- Не придумывай параметры, которых нет во входной спецификации
- Не придумывай дефолтные значения без явного указания
- Если информации не хватает, помечай это как `TBD`
- Required поля помечай явно
- Не смешивай факты из спецификации с предположениями

Формат ответа:
## {{method}} {{path}}

Короткое описание

### Аутентификация

### Параметры
Таблица с колонками:
- Имя
- Где передаётся
- Тип
- Обязательность
- Описание

### Request example
Кодовый блок

### Response example
Кодовый блок

### Ошибки
Таблица:
- Код
- Когда возникает
- Что значит

### Примечания

Если по одной endpoint-спецификации можно корректно дополнительно вывести ограничения или edge cases, добавь отдельный раздел `### Edge cases`.
```
