# Стандарты библиотеки промтов

> 🇷🇺 **Русский** · [🇬🇧 English](../en/standards.md)

[← Index](./README.md)

> Единые правила, по которым устроен каждый промт в этой папке. Если правишь существующий промт или добавляешь новый — сверяйся отсюда.

Эталонная карточка: [_template](./template.md)

---

## 1. Поведение при нехватке данных

В каждом промте должно быть единое правило: что модель делает, если контекста для качественного ответа не хватает. Без него поведение в разных промтах разное — иногда модель задаёт вопросы, иногда молча придумывает.

Канонический блок (вставляй буквально, число вопросов подбирай под сложность):

> Если для качественного ответа не хватает контекста — задай до N коротких уточняющих вопросов одним сообщением. Если критичных пробелов нет — действуй с разумными дефолтами и в начале ответа приведи раздел `Допущения` со списком того, что ты предположил.

Число вопросов по сложности промта:

- Простые (API документация, Docker, GraphQL) — до 3
- Средние (REST API, K8s, CI-CD, WebSocket, нагрузочное, API тесты) — до 5
- Сложные (Архитектура, Review, FastAPI шаблон) — до 7

## 2. Definition of done

Каждый промт заканчивается разделом `Definition of done` — критерии, при которых ответ считается готовым. Универсальный минимум, применимый ко всем промтам:

- Все запрошенные разделы присутствуют и не свёрнуты в одну строку
- Команды, код и конфиги — в fenced code blocks с указанием языка
- Нет vague формулировок: «проверь что всё ок», «настрой по необходимости», «адаптируй под себя»
- Допущения отделены от фактов в явный раздел `Допущения`
- Если промт просит таблицу, диаграмму или чек-лист — они реально приведены, а не заменены текстом
- Если ответ обрезан по длине — последний выведенный раздел всё равно завершён, не висит на полуслове

Сверху докладываются критерии под конкретную задачу. Примеры:

- FastAPI шаблон: «дерево каталогов содержит все указанные подпапки», «каждый ключевой файл приведён целиком, без `same as above`»
- Runbook: «у каждого шага есть конкретная команда или критерий успеха»
- Архитектура: «есть Mermaid контейнерного уровня», «таблица рисков заполнена для всех перечисленных рисков»

## 3. Приоритизация длины и разбиение

Тяжёлые промты (≥ 6 разделов в ответе или ≥ 5 файлов на выходе) поддерживают два режима:

- `quick` — всё в одном ответе. Для драфта, прототипа, ознакомления.
- `staged` — план → подтверждение → исполнение по шагам. Для серьёзной задачи, где цена ошибки высока.

В блоке `Что подставить` добавляется `{{mode}}` со значениями `quick | staged`.

**Для `quick` режима** разделы ответа помечаются:

- `[обязательно]` — пропускать нельзя
- `[если останется место]` — можно сократить, но не пропускать

Mermaid-диаграммы, executive summary и таблицы рисков помечаются `[обязательно]` всегда.

**Для `staged` режима** в начале промта добавляется блок:

> Сначала составь короткий план (3-7 пунктов) того, как ты подойдёшь к задаче и в каком порядке будешь выдавать результаты. Жди подтверждения. Не начинай исполнять до подтверждения. После подтверждения исполняй по одному пункту плана за раз и каждый раз ожидай ответа `дальше` или правок.

Простые промты (API документация, Docker, Runbook, GraphQL для маленького домена) — оставляем single-shot, режимы не вводим.

## 4. Жанры

Каждый промт принадлежит одному из четырёх жанров. Жанр проставляется тегом в шапке и колонкой в `00-Index.md`.

| Жанр | Тег | Когда подходит |
| --- | --- | --- |
| Single-shot | `#single-shot` | Инструкция → большой ответ. Default для простых задач. |
| Staged | `#staged` | План → подтверждение → исполнение по шагам. Для тяжёлых задач, где первая попытка дорого ошибается. |
| Critique | `#critique` | Draft → self-review → improve. Для review, QA, аудита. |
| Interview | `#interview` | Модель задаёт вопросы, дожидается ответов, потом действует. Для задач, где контекста объективно мало. |

Один промт может поддерживать два жанра внутри одной карточки через `{{mode}}` — например, Архитектура: `staged` как основной режим + `quick` как fallback. В этом случае в шапке проставляются оба тега. Дублировать файлы не нужно.

## 5. Плейсхолдеры

- Имена — на английском, snake_case: `{{service_name}}`, `{{auth_method}}`. Текущая русская нотация в «Архитектура микросервиса» (`{{домен}}`, `{{бизнес_цель}}`) — на миграцию.
- Формат — двойные фигурные скобки: `{{...}}`
- В блоке `Что подставить` каждый плейсхолдер сопровождается типом и примером:
  - `{{service_name}}` — string, e.g. `payments-api`
  - `{{auth_method}}` — enum: `jwt | oauth2 | api_key | mtls`
  - `{{replica_count}}` — int, e.g. `3`
- Если плейсхолдер реально не влияет на вывод — выкинуть. Сейчас такой есть: `{{specification_format}}` в REST-промте задекларирован, но промт всё равно жёстко требует OpenAPI.
- Технологические допущения, которые могут отличаться между командами (версии языка, ORM, линтер, тест-фреймворк), выносятся в плейсхолдеры, а не зашиваются в тело промта.

## 6. Антипримеры

Где это применимо (документация, YAML, схемы, кодогенерация), добавляй блок `Не делай так:` с 1-2 строк негативного примера. Это работает сильнее, чем абстрактные запреты вроде «не делай RPC под видом REST».

Пример формата:

```
Не делай так:
- POST /users/getById — это RPC под видом REST. Используй GET /users/{id}.
- 200 OK с телом {"error": "..."} — статус и тело должны соответствовать.
```

## 7. Источник идеи и дельта

Если промт собран по мотивам внешнего источника:

- `**Источник идеи:** [Название](URL)`
- `**Дельта от оригинала:**` — что добавлено, убрано или переработано (1-2 строки). Без дельты ссылка декларативна и не даёт ответа на «а в чём ценность *моей* версии».

Метрики типа «`4,612 copies · 4.3/5`» с внешних сайтов не сохраняем — это маркетинговый шум, не сигнал о пригодности в нашем контексте. Внутренний эквивалент — `**Использовался:** N раз, последнее использование YYYY-MM-DD` — пока ведём вручную при необходимости.

## 8. Метаданные карточки

Шапка карточки содержит:

- `**Статус:**` — один из:
  - `📋 Template` — каркас, нужно дорабатывать под кейс
  - `🟢 Ready` — проверен, можно использовать без доработок
  - `🧪 Experimental` — собран, но мало прогонов
- `**Owner:**` — кто отвечает за актуальность
- `**Последняя правка:**` — ISO дата (YYYY-MM-DD)
- `**Версия:**` — простой счётчик: `v1`, `v2`...

## 9. Соглашение о языке

- Тело карточки и пояснения — русский.
- Имена плейсхолдеров и технические термины (`auth`, `idempotency`, `health check`, `staged`, `rollback`) — английский.
- Внутри одного промта стиль согласован: либо «аутентификация», либо `auth`, но не оба в соседних строках.

## 10. Чек-лист для нового промта

Перед коммитом нового или отредактированного промта проверь:

- [ ] Шапка карточки заполнена по [_template](./template.md)
- [ ] Проставлены теги темы и жанра
- [ ] Есть блок «Поведение при нехватке данных» с числом вопросов
- [ ] Есть раздел `Definition of done` с минимумом + специфичными критериями
- [ ] Плейсхолдеры на английском snake_case, у каждого тип и пример
- [ ] Если промт тяжёлый — поддержан `{{mode}}` со значениями `quick | staged`
- [ ] В `quick` режиме разделы помечены `[обязательно]` / `[если останется место]`
- [ ] Где уместно — добавлен блок «Не делай так:»
- [ ] Указан источник и дельта от оригинала (если применимо)
- [ ] Карточка добавлена в `00-Index.md` с колонкой жанра
